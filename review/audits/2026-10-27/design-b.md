# Candidate B: domain-owned operations, durable storage decisions

## Problem
Delb already uses collection membership as visibility and has a cover journal plus Unraid-safe fallback. Other paths independently mutate the same database and files; this causes bypasses, irrecoverable inputs and rank drift. Repair at domain boundaries without a generic workflow engine or unrelated UI rewrite.

## Caller's view
```ts
// collection bulk handler; source visibility checked before any link is added
const result = await assignVisibleBooks({ userId, sourceCollectionId, requestedIds, targetChanges });
// status handlers (single and bulk)
const result = await transitionBookStatuses({ userId, visibleBookIds, status, now });
// storage caller describes domain intent, not phases or journal manipulation
await replaceBookFile({ bookId, source: stagedUpload, format });
await moveBookStorageToCanonical({ bookId });
await deleteBook({ bookId });
```

## Shape
- `collections/visibility`: `visibleBooks(userId, ids): Promise<Set<BookId>>` and reusable SQL membership predicate, with consistent nonexistent/inaccessible response; collection assignment checks source visibility in same write transaction as link insertion and destination edit rights. Source visibility derives from *any* accessible collection; target need not equal source, preserving authorized resharing. Personal collection restrictions remain enforced. Duplicate search and entity metadata use the same visible-book relation, no global candidate leakage. Authorize collection management before looking up emails. Owner role changes/transfer happen in one transaction with owner invariant and explicit deletion policy.
- `books/status`: `transitionBookStatuses({ userId, visibleBookIds, status: ReadingStatus | null, now }): Promise<{updated:number; cleared:number}>`. One SQLite write transaction, conflict-safe upserts and actual counts, common status date rules, deterministic contiguous TBR reranking for the user after all transitions including clear and bulk. Preserve intended rank order; serialize writers at database transaction boundary. Existing endpoint payload compatibility retained.
- `books/storage`: domain operations, not generic user-supplied callbacks. Private typed journal `{version, operationId, bookId, kind: 'move'|'replace'|'delete'|'create', entries: {source?, target?, staged?, backup?, size, digest}[]}`. Persist durable prepared journal, fully stage/verify all new data and move originals to recoverable backups as needed; a durable operation ID/commit marker in the SAME DB transaction as path/row changes is the decision authority, not cover path equality. Before marker, recover rollback; after marker, recover rollforward and cleanup. File targets installed before commit or otherwise never expose DB paths to absent files; deletion holds originals in reversible staging before DB deletion. Retain journal and any unique copies when recovery/cleanup fails, report failures. Fsync files/journal and directory where supported; do not claim power-loss guarantees beyond filesystem behavior. Exclusive destination creation; existing destinations never imply equality: compare verified bytes or reject and preserve both. Include sidecars; never delete a source until verified destination and committed DB decision. Cross-device/Unraid EXDEV and EUCLEAN fallback must retain COPYFILE_EXCL, sync and SHA-256, without broadening fallback to arbitrary errors.
- Cover transaction currently commits DB before rollforward and recovery infers success via path equality; same-path updates require operation marker, not inference. Use the same per-book coordinator for all destructive operations, covering recovery as well as active work. In-process lock only suffices if single process is actually enforced; otherwise use durable cross-process ownership, with stale-owner recovery and no expiration of live work. Do not steal a lease merely on elapsed time. Bootstrap recovery must complete before traffic/watcher, under same ownership rule. Multi-book operations need stable lock order, and database transactions must be short, never held while copying large files.
- Dropbox: operation-specific processing claim with identity and original name; restart reconcile claims based on durable operation decision; preserve input on failure. Failed destinations use unique IDs plus exclusive creation. Create/import upload stage first, then one SQLite transaction for book, normalized relations and membership; cleanup only confirmed staging after commit or safe rollback.
- `external-image`: one operation validates each URL and all resolved IPv4/IPv6 addresses, including mapped and non-global ranges, then pins actual socket lookup to validated address while retaining original host, TLS SNI, hostname certificate verification. Redirect re-resolve/revalidate/re-pin; disable proxy or validate proxy behavior; constrain timeout, bytes, content and decoded dimensions. Raster decode/re-encode and serve safe type with nosniff; refuse SVG and spoofed active formats. Reader disables scripted EPUB content (and verifies resulting sandbox/origin) unless isolation can guarantee parent separation; test both reading modes and representative books. Limit upload/archive size and extraction expansion before materialization.
- Client: request generations scoped to input/account; immediately invalidate prior work on change, abort where possible, guard success/error/loading commits, and always start latest request. Reader uses latest-navigation version, flushes pending location during in-app navigation and accounts for browser lifecycle limits; settings pull merges by per-field local edit version. Reset account-scoped filters on logout. Provider requests settle independently. Use native accessible controls and dialog/combobox focus management, without changing styling.
- Other localized contracts: half-star integers, cursor unit matching SQLite, metadata normalization plus DB transaction, realpath Calibre containment, entity SQL pagination with bounded previews. Separate CI/Node/dependency updates; frozen install and publishing depends on successful test for identical revision. Treat A36 as unmeasured and R01/R02 as hypotheses until controlled tests.

## Rationale and alternatives
Expose domain intents and results while one owner hides durable phases and path policy. No broad storage rewrite: adapt existing cover implementation and verified-copy functions, but replace its ambiguous recovery discriminator. Alternative 1: patch every endpoint independently; shallower calls but leaks persistence and authorization invariants to every caller and reproduces divergence. Alternative 2: general distributed saga framework with pluggable callbacks; exposes phase sequencing, rollback and recovery policy and introduces unnecessary state machinery. Candidate uses a narrow private shared storage protocol and separately owned visibility/status operations.

## Tradeoffs and risks
A durable DB marker/migration adds state and cleanup but resolves crashes after commit before journal update. Crash atomicity depends on filesystem durability and atomic database behavior; test process-kill checkpoints, do not claim real power-loss or multi-host guarantees without evidence. Exclusive file installs and failed cleanup can leave recovery artifacts by design. Need verify existing DB driver supports actual transactions and locking semantics, recovery on same-path updates, and whether multiple server processes can run against one library. Cover-format changes may affect compatibility; require real browser representative corpus and socket-level DNS/redirect tests. Resource constraints must preserve reasonable books.

## Implementation partitions
1. Server authorization, status, metadata contracts, indexes, input confinement. Own server endpoints/domain SQL except storage and image.
2. Storage and ingestion: move/delete/replacement/create coordination, cover recovery, Dropbox; own `server/utils/books` storage/cover/dropbox and tightly coupled endpoints. Agree operation interface and marker migration before others touch paths.
3. Client and untrusted content: async ownership, accessibility, reader isolation, remote image transport/limits; own app/reader plus external-image endpoint and transport. Integration lead handles CI, dependencies, container/onboarding and shared tests; no competing edits to storage files.

## First step
Prove visibility and lossless-recovery cases on baseline, then settle DB transaction/locking and recovery marker design before adapting the first destructive path. Synthesis decision belongs to orchestrator.
